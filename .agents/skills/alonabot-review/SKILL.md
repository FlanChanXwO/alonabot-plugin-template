# 审查插件

本技能用于只读审查和交付前自审。较大改动使用独立审阅者，可用时同时加载 `code-review-expert`；不可用时按以下项目检查，不能只凭测试通过给出认可。

## 固定对象

检查 `git status -sb`、范围 diff 与 stat，记录 base 和 head 的完整 SHA。PR 没有工作区 diff 不表示分支没有改动。读取原始需求或 Issue 与[编码规范](../../../docs/coding-standards.zh-CN.md)。未获修复授权时不改源文件。

## 分开审查两条轴

**Spec**：追踪输入到输出、副作用与失败路径；检查是否经 SDK 与 Core 通信、身份与权限是否来自可信字段、取消与停止是否传到底、资源是否释放。以需求和现行行为判断缺陷，不把需求没有承诺的能力当作遗漏。

**Standards**：以 Google Go Style Guide（可用时加载 `go-google-style-*` 技能）和[编码规范](../../../docs/coding-standards.zh-CN.md)为准，检查语义所有者、接口是否减少调用者负担、类型与常量是否就近、错误链和资源生命周期。按[注释技能](../alonabot-code-commenting/SKILL.md)核查包文档、命名术语、文档注释与 step 注释，检查防御性的多余检查、缺少实际发布基线依据的兼容层，以及提交的测试是否只有集成测试。判断性建议不能冒充硬规则。

核对生成源、资源、使用文档与 changelog 是否同步。已有检查可覆盖的内容不重复索要测试；外部平台验证缺失要明确写出，不能用模拟端顶替。

## 输出可执行结论

每项问题给出文件与行号、触发条件、用户影响和最小修复。严重度按影响给出：P0 立即阻断，P1 合并前修复，P2 一般缺陷或维护风险，P3 可选建议。只列可证实的问题。

两条轴分别报告，最后说明是否建议合并、关键证据和真实缺口。审查请求不等于写入授权。同一账号不能对自己的 PR request changes，改用 PR 评论。
