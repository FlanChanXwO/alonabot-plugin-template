# 编写 AlonaBot 注释

本技能把 [编码规范](../../../docs/coding-standards.zh-CN.md)「包文档」「注释」两节用到实际代码上。通用原则来自 `code-commenting` 技能：只写名字和结构表达不出来的东西。两者冲突时以编码规范为准。

## 先读懂再写

读完目标文件、完整的类型和函数，核对调用者、状态和错误语义，确认代码实际做了什么再写。不推测代码没有提供的保证，例如原子性、线程安全、幂等或可回退。

## 写什么

- **包文档**：每个包只在一个文件里写，参照 Go 标准库：第一句以 `Package x` 开头说清包做什么，再分段写范围、不负责什么和规格条款。其他文件开头不写注释，不写维护者和日期。build tag 和生成指令保持原位；生成的文件不补写。
- **文档注释**：导出声明都写，以标识符开头、紧跟动词，例如「Reserve 占用 n 字节……」。不写「X 是……」的定义句，不用「该函数」「此方法」「用于」开头。私有函数在名字和签名说不清时才写。
- **字段**：只在名字和类型看不出时写，例如单位、零值的意义、可选性、锁保护、所有权和生命周期。短说明放在行尾。
- **step 注释**：有几个明确阶段的函数，在每段前写 `// 1. ...`，说明目的或顺序要求。编号的是阶段，不是语句。
- **基础工程师读得懂**：`select`、channel 关闭、atomic、锁顺序、goroutine 交接旁边写一行原因；特别复杂的模块在类型或文件开头用多行注释讲清整体模型。
- **现状**：只写当前行为、限制和原因，不写工作包、切片、goal 或 task 编号，也不写「后续补齐」这类进度；临时实现用 `shortcut: <限制>，<替换条件>`。

## 不写什么

逐行复述代码；给每个赋值、`if err != nil` 或 return 加注释；只是把名字换一种说法的注释；装饰性的分隔线；代码没有提供的保证。

## 自审

- 注释与最终代码一致，编号与真实阶段对应，build tag 和生成指令的位置没有动。
- 新增文件完整检查；已有文件检查包文档和本次触及的部分。全库补齐是单独的任务，不要把局部完成说成全仓符合。
- 只改注释时，运行格式检查和 diff 检查即可。
- 注释工作不等于获得了重命名、拆函数或修改行为的授权；发现这类问题时单独报告。
